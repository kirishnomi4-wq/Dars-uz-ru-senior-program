9.title = Entity описывает таблицу, миграция её создаёт, таблица migrations помнит, что запускалось
9.seg.a.key = Entity — <b>таблица в виде кода</b>: класс, колонки через decorator
9.seg.a.voice = Посмотрим, что происходит внутри первого этапа. В TypeORM таблица описывается классом entity: decorator Entity даёт имя таблицы, decorator Column — каждую колонку. В знакомом вам Mongoose это была schema.
9.seg.b.key = Миграция — <b>SQL-файл, создающий таблицу</b>; <code>synchronize</code> выключен
9.seg.b.voice = Таблицу создаёт не entity, а миграция. Миграция — обычный SQL-файл: в методе up create table, в методе down drop table. Synchronize false, то есть TypeORM сам таблицу не меняет. В Mongoose миграций не было, потому что у коллекции нет правил колонок. В PostgreSQL правила есть, и меняем их файлом.
9.seg.c.key = Таблица <code>migrations</code> — <b>помнит, какой файл запускался</b>; при подъёме сервера незапущенные запускаются сами
9.seg.c.voice = Когда миграция прошла, TypeORM пишет в таблицу migrations одну строку: имя файла и время. При каждом подъёме сервер смотрит в эту таблицу и запускает только незапущенные миграции, это настройка migrations run true. При втором запуске ничего не повторяется.

9.seg.d.voice = Итог: entity описывает таблицу в коде, миграция создаёт её в базе, таблица migrations помнит, какой файл запускался. Если потом захотите добавить колонку — пишете новую миграцию. Править уже запущенную миграцию бесполезно: база её заново не запустит.
