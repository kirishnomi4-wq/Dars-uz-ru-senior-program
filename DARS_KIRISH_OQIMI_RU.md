# Поток входа в урок — проверка по группе ментора (MVP)

Статус: **проектное предложение**. Код не написан, файлы платформы не изменялись.
Связанные документы: `API_INTEGRATION.md` (School Data API v1), `LMS_INTEGRATSIYA_TZ.pdf`.

## 1. Цель

Ментор открывает урок → войти могут **только ученики выбранной им группы**.

Сейчас вход по PIN: кто знает PIN — тот и вошёл. Задача: вместо PIN (или поверх него)
проверять **реальное членство в группе**.

Жёсткое условие: **при отказе backend урок не останавливается.** Ужесточается вход, а не обучение.

## 2. Три стороны — кто что знает

| Сторона | Знает | Не знает |
|---|---|---|
| **LMS** | кто вошёл (токен), роль, имя, язык (`lang`) | баллы внутри урока, состояние сессии |
| **Наш backend** | сессия (урок + группа + PIN), баллы, арена | в какой группе ученик |
| **School Data API** | ученик → подписка → группа → преподаватель | урок, сессия, баллы |

То есть на вопрос «этот ученик в этой группе?» отвечает **только School Data API**.

## 3. 🔴 Пробел, который нужно закрыть

**School Data API не отдаёт список групп ментора.**

Причина: для ученика есть две точки входа (`/students/{crmId}/…` и `/lms/students/{lmsId}/…`),
а **для преподавателя такой точки нет**. Преподаватель виден только внутри контекста ученика
(`data.subscriptions[].group.teacher.id` — это CRM `teacher_list.ID`).

Значит вопрос «вошедший в LMS ментор = какой преподаватель в CRM?» этим API не решается.

**Решение:** список групп ментора должна отдавать **LMS** (там эти данные есть). Подробнее — раздел 7.

## 4. Что хранит наш backend

Достаточно одной таблицы:

```
session
  id
  lesson_id        -- например 'pm-m1d2-v1'
  group_id         -- CRM group_list.ID — выбранная ментором группа
  mentor_id        -- идентификатор ментора из LMS
  pin              -- текущий PIN (остаётся как резерв)
  status           -- open | closed
  created_at
```

Для кеширования состава группы:

```
session_group_cache
  session_id
  student_lms_id   -- ученики группы (пишется один раз при открытии сессии)
  fetched_at
```

## 5. Поток A — ментор открывает урок

1. Ментор нажимает «Открыть урок» (токен: `mentor_id`, роль `mentor`).
2. Backend читает список групп ментора из токена/контекста LMS.
3. Backend показывает выбор группы; одна предвыбрана по расписанию.
4. Ментор подтверждает группу → создаётся `session` (`lesson_id` + `group_id` + PIN).
5. Backend заранее выгружает состав группы в `session_group_cache`.
6. Ментору показывается PIN, сессия готова.

**Окно выбора группы** обязательно — у ментора несколько групп:

```
С какой группой проводите урок?
  ● F7-A   16:00, сегодня       ← предвыбрано
  ○ F7-B   18:00, вторник
  ○ M3-C   14:00, суббота
```

Предвыбор считается по `group_list.days` («1,3,5») и `group_list.start_time` («16:00») —
берётся группа, ближайшая к текущему дню и времени. Обычно ментор просто подтверждает: один клик.

> Почему не полностью автоматически: уроки переносят, менторов заменяют, бывают сдвоенные занятия.
> В этих случаях автоматика ошибается, а ментор — нет. Выбор остаётся за человеком.

## 6. Поток B — ученик входит

1. Ученик открывает урок (токен: `lms_student_id`, `lang`).
2. Backend проверяет `session_group_cache`.
3. **Если найден** — впускаем.
4. **Если не найден** — запрос:
   `GET /api/v1/lms/students/{lmsStudentId}/integration-context`
5. Из ответа берём `data.subscriptions[].group.id`.
6. Сравниваем с `session.group_id`.
7. Совпало — впускаем. Не совпало — «Вы не состоите в этой группе».

Ядро проверки — одно условие:

```
session.group_id ∈ response.data.subscriptions[*].group.id
```

## 7. Что требуется от разработчика LMS

Вместе с токеном нужно передавать (подлежит согласованию):

- [ ] **роль** — `mentor` или `student`
- [ ] **для ученика:** `lms_student_id` (это `student_students.id` — ключ для
      `/api/v1/lms/students/{id}/integration-context`)
- [ ] **для ментора:** список его групп — `group_id` (CRM `group_list.ID`) + название + `days` + `start_time`
- [ ] **`lang`** — `uz` | `ru` (уже передаётся)
- [ ] имя — для отображения на экране

🔴 Третий пункт критичен: без него ментор не сможет выбрать группу (см. раздел 3).

## 8. Обработка ошибок — резерв обязателен

| Ситуация | Решение |
|---|---|
| API вернул `200`, группа совпала | ✅ Впускаем |
| API вернул `200`, группа не совпала | ⛔ Не впускаем |
| API вернул `404` | ⚠️ **Вход по PIN** — `404` не различает «нет ученика» и «нет прав» |
| API вернул `429` | ⚠️ **Вход по PIN**, соблюдаем `Retry-After` |
| API вернул `503` / сетевой сбой | ⚠️ **Вход по PIN** |
| API вернул `401` | ⚠️ **Вход по PIN** + уведомить администратора (проблема с токеном) |
| Токена нет вовсе | ⚠️ **Вход по PIN** (текущее поведение) |

**Правило:** проверка — это только *дополнительный замок*. Если он не сработал, старая дверь
остаётся открытой. Урок никогда не останавливается из-за backend.

## 9. Ограничения, о которых нужно знать заранее

- **Замороженная подписка в группе не видна.** API возвращает только `ACTIVE = 1` и
  `STATUS IN ('active','demo')`. Статусы `freezed` и `archive` не попадают в ответ.
  Ученик с приостановленной оплатой проверку не пройдёт — здесь тоже сработает резерв по PIN.
- **Массового запроса нет.** Один ученик = один запрос. Поэтому состав группы выгружается
  заранее при открытии сессии (раздел 5) — чтобы не упереться в `429`, когда в начале урока
  25 учеников нажимают одновременно.
- **У одного ученика может быть несколько LMS ID** (`lms_student_ids` — массив).
- **Гарантии снимка нет** — состав группы может измениться. Для MVP время жизни кеша равно
  длительности сессии.
- **Токен только на сервере.** Не должен попадать во frontend, логи или query string.
- **`X-Request-ID`**, если присутствует в ответе, записывать в лог — понадобится для аудита.

## 10. Не входит в MVP

- автоматическое добавление ученика в группу (API только читает, `GET`)
- автоматическое открытие урока по расписанию
- отслеживание изменений состава группы в реальном времени
- автоматическое сопоставление преподавателя с CRM (пробел из раздела 3)
